# Составной индекс для истории поездок пассажира

## Контекст и проблема

Экран истории показывает пассажиру 20 последних поездок. Запрос в src/handlers.ts: `WHERE passenger_id = $1 ORDER BY created_at DESC LIMIT 20`. В таблице trips был только индекс первичного ключа trips_pkey, поэтому PostgreSQL проходил по всей таблице: Parallel Seq Scan по 2 000 000 строк, около 54 тыс. буферов, 98.693 ms на один запрос.

В нагрузочном замере baseline (reports/baseline.md) p95 истории 157.29 ms при цели меньше 50 ms (design.md, раздел «Требования»). Цель не выполнена в 3.1 раза, ошибок и dropped iterations нет. Время растёт вместе с таблицей: за год набегает около 73 млн поездок, то есть в десятки раз больше, чем на стенде.

## Какие варианты сравнивали

1. Составной индекс `(passenger_id, created_at DESC)`. Совпадает с фильтром и сортировкой: строки одного пассажира лежат в индексе уже в нужном порядке, Limit берёт первые 20 и останавливается. Дополнительные операции сортировки не нужны.
2. Индекс только по `passenger_id`. Дешевле по размеру, но запрос читает все около 200 поездок пассажира и сортирует их; с ростом числа поездок на пассажира работа растёт. Этот вариант в замере не проверяли, вывод сделан по плану запроса.
3. Без изменения схемы: читать историю с реплики (READ_HISTORY_FROM_REPLICA=true) или добавить кэш. Реплика переносит тот же полный проход по таблице на другой сервер, а кэш не помогает первому обращению каждого пассажира; причина (отсутствие индекса) остаётся.

## Решение

Выбран вариант 1. Миграция db/migrations/007-trips-passenger-history-index.sql создаёт индекс `trips_passenger_created_at_idx` на `trips (passenger_id, created_at DESC)` командой `CREATE INDEX IF NOT EXISTS`. Миграции в migrate.ts применяются заново при каждом запуске, поэтому повторный запуск безопасен: проверено двумя запусками подряд, ошибок нет.

## Последствия

Плюсы (reports/after-index.md, тот же профиль mixed, те же 2 000 000 поездок):

- p95 истории 157.29 ms → 3.04 ms при цели меньше 50 ms;
- план запроса: Index Scan вместо Parallel Seq Scan, 26 буферов вместо около 54 тыс., Execution Time 0.182 ms вместо 98.693 ms.

Цена:

- дополнительное место: индекс занимает 60 МБ (около 14% от 423 МБ данных таблицы); trips вместе с индексами выросла с 466 МБ до 526 МБ;
- стоимость записи: каждая вставка в trips и каждое изменение created_at или passenger_id теперь обновляет второй индекс; при 9.26 созданиях в секунду в пике это допустимо, но влияние на создание поездки отдельно не измеряли;
- индекс нужно держать в памяти, чтобы история оставалась быстрой; при росте таблицы в десятки раз он перестанет помещаться в кэш у небольшого сервера.

## Подтверждение

- Замеры: [reports/baseline.md](../../reports/baseline.md) и [reports/after-index.md](../../reports/after-index.md), один профиль load/profile.json и одни данные (2 000 000 поездок, 10 000 пассажиров).
- План запроса: EXPLAIN (ANALYZE, BUFFERS) в обоих отчётах; в after-index.md используется trips_passenger_created_at_idx.
- Повторный запуск `make migrate` не падает.

Условие отката: удалить индекс (`DROP INDEX IF EXISTS trips_passenger_created_at_idx`), если замер создания поездок на профиле с реальной долей записи покажет, что p95 создания вырос более чем вдвое из-за индекса, или если после роста данных план истории перестанет использовать индекс и p95 истории снова превысит 50 ms.
